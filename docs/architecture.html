Architecture

How the layers compose.

Sera for Agents is a stack of independent layers, and the bottom one is now a chain of our own. Pick the highest layer that solves your problem; everything below it is implementation detail.

Layers explained

1. Sera appchain

A purpose-built chain for stablecoin FX. The central limit order book is not a contract deployed on a general-purpose chain — it is the chain's state machine. Makers post quotes, takers cross them, and a fill is final in the block that contains it. Not a DEX. Not an AMM. Think Visa, not Uniswap.

Accounts, agent keys and mandates are native objects, so a mandate is checked as part of state transition validity rather than by whatever client happens to be calling. Fees are taken in the stablecoin being swapped; there is no gas token.

Its relationship to Ethereum. Every state transition carries a validity proof settled on L1, deposits arrive through an L1 deposit contract, and withdrawals leave to L1 — including request_forced_withdrawal, which works from Ethereum alone if the sequencer stops responding. The data needed to reconstruct balances is published rather than held.

2. Sera REST API (api.sera.cx/api/v1)

The canonical interface to Sera Protocol state. Token registry, market catalog, FX rates, quote generation, execute. Every higher layer routes through this.

3. sera-mcp (the MCP)

55 tools exposed over the Model Context Protocol — stdio JSON-RPC — plus 13 more for accounts, funding, receipts and forced exit. Wraps the REST API with the EIP-712 quote→sign→execute flow, a dry-run kill switch, server-derived notional, and uuid-route_params binding. Self-contained: no SDK, no signer, no key handling.

On policy. The MCP used to be where notional caps and recipient allowlists were enforced, which held only as long as the agent kept using it. Those limits now live in the mandate on the agent key, enforced by the chain; the MCP sets them, mirrors them and surfaces mandate_remaining. Its client-side gates remain as a seatbelt, not as the safety story.

Versioning. v1 targets mainnet as it works today and keeps existing installs untouched; v2 targets the appchain and is the default for new installs.

Why an MCP? Because every modern agent host (Claude, Cursor, ChatGPT, OpenClaw, Hermes, NanoClaw) speaks MCP natively. Three lines of config and your agent has 55 FX tools.

4. x402 (HTTP payments)

For callers that speak HTTP rather than MCP. Because settlement is now Sera's own chain, Sera is the x402 facilitator itself: a managed endpoint arrives on agents.sera.cx at appchain launch, with nothing to deploy. x402-service remains in the repo as a thin Express server for operators who want to hold their own key; run it against the appchain testnet with npm run testnet, which exercises the production code path rather than mocking the payment and swap legs.

Two directions matter. Receiving: an agent on Base or Ethereum mainnet pays USDC over plain x402 with no Sera account, the payment lands in Sera's gateway, converts in-ledger, and credits the merchant in its own currency. Native: two Sera accounts settle a 402 invoice in-ledger — instant, no bridge, fee in the stablecoin paid.

5. Templates & bundled agent

Pre-wired starter projects (terminal chat, web chat, webhook responder) and a complete bundled Sera Agent — useful when you want one-command-to-run rather than configure-from-scratch. The three starters use a local stdio MCP by default; set SERA_MCP_URL to connect them to a Streamable HTTP MCP instead.

Two execution paths

Use the MCP path directly, or the x402 path when the caller speaks HTTP:

Path 1 — MCP (the default)

  • Agent host (Claude, Cursor, etc.) loads sera-mcp at startup.
  • Agent calls sera.get_quote — gets back a firm quote with the KYT/KYA result attached and EIP-712 typed-data.
  • Agent's wallet client signs the typed-data with its agent key (the MCP never sees the key).
  • Agent calls sera.execute_swap with the signature; the chain validates the mandate as part of the state transition.
  • Settlement is final in that block — nothing to poll. sera.get_receipt returns the signed receipt, and sera.verify_receipt checks it against the L1 state root.

Path 2 — x402 over HTTP

  • The caller hits POST /x402/swap — on agents.sera.cx for the managed facilitator, or on your own deployment of x402-service.
  • Server returns 402 Payment Required + a payment_id.
  • Caller pays USDC (EIP-3009 transferWithAuthorization) and retries with the X-PAYMENT header.
  • The facilitator verifies the payment, converts in-ledger on the appchain, and credits the recipient in the target currency.
  • Returns 200 OK with the delivered amount + receipt_id.
  • If both parties already hold Sera accounts, skip the USDC leg entirely: the invoice settles account-to-account in-ledger.

Trust boundaries

What the MCP can do

  • Read everything from Sera REST (rates, markets, history, deals).
  • Generate signed-typed-data quote objects for the agent's wallet to sign.
  • Submit pre-signed quotes for execution.
  • Set and mirror the mandate on an agent key, and report what is left of it.
  • Apply its own client-side gates — dry-run-only mode, local caps — on top of the chain's.

What the MCP cannot do

  • Hold or read a private key (signer is always the agent's wallet client).
  • Move funds without an externally-signed quote.
  • Bypass its own policy gates from inside a tool call.
  • Exceed the mandate. A client-side gate can be swapped out; the chain's check cannot.

What the appchain guarantees

  • Balances are proven to Ethereum with validity proofs, not asserted by an operator.
  • Withdrawal is possible from Ethereum directly, with a bounded delay, if Sera stops responding.
  • Sera cannot freeze or seize funds, censor intents, or reorder fills — matching rules are proven per block.

x402 trust model

An x402 facilitator holds the USDC inflow for the duration of the swap — that is true of the managed endpoint and of your own deployment alike. What used to be a "vault wallet" is now a Sera account with an agent key, so the same mandate limits apply to it: a cap, an allowlist, an expiry. Use the MCP path if you want the owner's own wallet to sign every leg, or the native in-ledger flow if both sides hold Sera accounts and no custodial hop is wanted at all.

Where to put your code

  • An MCP plugin / agent skill — call sera.* tools, no extra infra needed. Cheapest, most flexible. See AI agent tutorial.
  • A web app — call sera-mcp from your backend (spawn it as a subprocess, talk JSON-RPC over stdio) OR self-host sera-agents/x402-service and call your deployment over plain HTTP. See payment widget + trading dashboard tutorials.
  • A smart contract — read Sera's reference rate from your contract via an oracle wrapper or call get_fx_rate off-chain and post it on-chain. See prediction market tutorial.
  • A cron job — call the bundled sera CLI from your scheduler. See treasury rebalancer tutorial.
  • An x402-paid API — wrap your own service in the same x402 pattern we use. See x402-paid API tutorial.
