Concepts

The pieces, explained.

Eight concepts you'll meet constantly: the appchain · accounts & mandates · receipts · CLOB · MCP · x402 · EIP-712 · EIP-3009. Each gets a one-paragraph definition, why we use it, and what changes if you swap it out.

The appchain — Sera is its own chain

Sera settles on a purpose-built chain rather than renting block space on a general-purpose one. Balances live in a ledger, the order book is the chain's state machine, and every state transition carries a validity proof settled on Ethereum. Deposits arrive from L1; withdrawals leave to L1; in between, nothing is a transaction in the usual sense.

Why it matters for your code

  • Instant finality. A filled quote is done in the block that contains it. There is no confirmation count, no reorg window and no pending state to poll.
  • No gas token. Fees are taken in the stablecoin you are swapping. Your agent never holds a second asset just to be able to move the first one.
  • No chain plumbing. No chain ID, no RPC endpoint, no nonce management. The MCP talks to Sera; Sera is the chain.
  • Native issuance. MYRT, XSGD and the other issuers mint directly in-ledger, so most of the currency set has no bridge leg at all.

What it does not change

Your signing stack. Intents are still EIP-712 typed data, still signed by whatever the owner already uses — a Safe, a hardware wallet, WalletConnect. The appchain did not introduce a new key type.

Accounts, agent keys and mandates

A Sera account is owned by one key and may authorise many. The owner key — a Safe or a hardware wallet — creates the account, authorises and revokes agent keys, and withdraws. An agent key belongs to one agent and can only act inside the mandate the owner attached to it.

What a mandate holds

  • A notional cap, denominated in the owner's home currency rather than in whatever asset is moving.
  • A pair allowlist — which markets this key may trade at all.
  • A destination allowlist — where it may send.
  • An expiry, after which the key is inert without anyone having to remember to revoke it.

Why this replaces client-side policy

Earlier versions of the MCP enforced USD notional caps in the client. That is a real safety feature right up until the agent runs a different client. On the appchain the mandate is enforced in the block: an intent that exceeds its cap, names an unlisted pair or sends to an unlisted destination does not fail politely in your process — it is not a valid state transition. The MCP sets and mirrors the mandate; it is no longer the thing holding the line.

Practically: call mandate_remaining before planning a large settlement, and treat revoke_key as the kill switch for a misbehaving agent.

Receipts — proof you can hand to someone else

Every settlement returns a signed receipt: pair, rate, amount in, amount out, fee, the KYT/KYA screening result, a timestamp, the block, the state root, and which agent key acted under which mandate.

Why a transaction hash isn't enough

A hash says something happened. A receipt says what happened, at what price, under whose authority — and binds the screening verdict to the moment of settlement rather than to a log somewhere else. verify_receipt checks a receipt against the L1 state root, so the party you paid can confirm it without trusting Sera and without trusting you.

What it's for

  • AP2 proof-of-payment. The receipt carries the fields the mandate-and-payment flow expects.
  • The owner's audit trail. export_receipts returns the full set, attributable per agent key.
  • Disputes. Rate and fee are in the signed object, so "what did we actually get filled at" has one answer.

CLOB — Central Limit Order Book

A CLOB is an order book where makers post limit orders (price + size, no market impact) and takers cross them. Trade price is exactly the limit price — no slippage curve, no constant-product math, no impermanent loss for liquidity providers.

Why we use one

FX needs price discipline. AMMs (Uniswap-style) work for volatile pairs because LPs accept inventory risk for swap fees, but stablecoin FX has tiny spreads and high notional — AMM impermanent loss eats the entire margin. CLOBs let market-makers quote the same spread they'd quote at any prime broker, on-chain.

Implications for your code

  • Quoted price = executed price. No slippage parameter to set.
  • If a quote returns "no liquidity," that's real — there's no maker at that level. Use scan_markets to find what is tradeable now.
  • Spreads tighten with notional density, not pool depth. A pair can be tight at $10K and loose at $100K, or vice versa.

MCP — Model Context Protocol

An open protocol from Anthropic for letting AI hosts (Claude, Cursor, ChatGPT, OpenAI Agents SDK, custom hosts) talk to external tools. Every host implements the same JSON-RPC over stdio interface; every tool is a server. Stewarded by the Linux Foundation as of 2026.

Why Sera ships an MCP

It's the most portable shape. One sera-mcp server reaches every modern agent host — no per-host SDK, no OAuth dance, no proprietary plugin format. "claude mcp add sera ..." and you have 55 FX tools.

What MCP gives you for free

  • Tools — typed function calls (sera.get_quote, etc.)
  • Resources — browseable static catalogs (sera://help/tools)
  • Prompts — slash commands the host surfaces in its UI (/deal_scan)

What it doesn't give you

  • Authentication. Each tool decides its own auth model (we use env-based API keys + EIP-712 signatures).
  • State persistence between calls. The MCP server's process is the only state.

x402 — HTTP 402 Payment Required

An open agent-payment standard layered on top of HTTP. The server returns 402 Payment Required with payment instructions. The client pays (USDC, on-chain). The client retries with an X-PAYMENT header. The server verifies and returns 200 OK with the goods. Idempotent, stateless, cache-friendly.

Managed, or your own

Some agents don't speak MCP — they speak HTTP. With settlement on the appchain, Sera acts as the x402 facilitator itself, so a managed endpoint arrives on agents.sera.cx at appchain launch. Self-hosting x402-service stays available for operators who want to hold their own key; point it at the appchain testnet with npm run testnet, which exercises the same code path as production rather than mocking it.

Two flows, not one

  • Receiving side. An agent anywhere pays USDC over plain x402 — on Base, on Ethereum mainnet — with no Sera account and no Sera knowledge. The payment lands in Sera's gateway, converts in-ledger, and credits the merchant in XSGD, MYRT, EURC or any of the 40.
  • Native side. Both parties already hold Sera accounts, so a 402 invoice settles account-to-account in-ledger: instant, no bridge, no approvals, no gas, and the payer's agent key stays inside its mandate.

Why this is interesting beyond Sera

x402 is the closest thing the agent ecosystem has to "Stripe for agents" without the Stripe. Wrapping any API in the same pattern means agents can pay you per call without contract negotiations, OAuth flows, or pre-funded API keys. See the x402-paid API tutorial.

EIP-712 — Typed structured-data signing

An Ethereum standard for hashing and signing structured data (instead of opaque hex strings). Wallets show humans "You are signing an Order: maker=0x...; price=1.41; expiry=...," not "Signature data 0xa3f7...8b2c."

Why we use it

Quote signing. Every Sera trade is a maker/taker order encoded as a typed-data struct (Maker · Market · isBid · BaseAmount · Price · Expiry · Nonce). The wallet signs that — never raw bytes. The sera-mcp never sees the private key; it just gets the signature back.

What you get

  • Phishing resistance. The wallet can show a humane summary.
  • Replay protection. The struct includes a nonce + chain_id.
  • Off-chain signing, on-chain settlement. No gas to ask for a quote.

EIP-3009 — transferWithAuthorization, on the funding leg

An ERC-20 extension that lets a token holder pre-sign an authorization to transfer X tokens to address Y by time T, which a third party then submits on-chain. USDC implements it. Its sibling EIP-2612 does the same for approvals.

Where it still applies

On the L1 side only — funding a Sera account, and receiving a standard x402 payment from an agent that lives on another chain. Without it, an agent paying for an API call would need an allowance approval and then a transfer: two transactions, two gas fees. With it, the agent signs off-chain, posts the authorization in the X-PAYMENT header, and the server submits it once.

Where it no longer applies

Inside Sera. Once funds are in the ledger, a payment is an intent against a balance — no token approval, no authorization to pre-sign, no gas for anyone to pay. If you are reading an older integration that treats EIP-3009 as the payment primitive, that is the L1 funding leg, not settlement.

Putting them together

Two end-to-end flows show how the concepts compose:

Setting up an agent (account + mandate)

1. Owner  -> sera.create_account          -> account, funded from L1 or native issuance
2. Owner  -> sera.create_agent_key        -> agent key, not yet useful
3. Owner  -> sera.set_mandate             -> cap, pairs, destinations, expiry
4. Agent  -> sera.mandate_remaining       -> knows what it is allowed to do

FX settlement on Sera (CLOB + MCP + EIP-712 + mandate + receipt)

1. Agent  -> sera.get_quote               -> firm quote + KYT/KYA result + Order struct
2. Agent  -> signs the Order via EIP-712 with its agent key
3. Agent  -> sera.execute_swap            -> chain checks the mandate, fills, settles
4. Chain  -> instant finality             -> no confirmations to wait on
5. Agent  -> sera.get_receipt             -> signed receipt: rate, amounts, block, state root
6. Payee  -> sera.verify_receipt          -> confirms it against the L1 state root

x402, receiving side (payer is on another chain)

1. Agent  -> POST agents.sera.cx/x402/swap -> 402 + payment_required + payment_id
2. Agent  -> signs USDC transferWithAuthorization (EIP-3009) off-chain
3. Agent  -> retries POST with X-PAYMENT: id:auth
4. Sera   -> verifies the USDC payment, converts in-ledger
5. Sera   -> 200 OK with delivered + receipt_id, merchant credited in its own currency

x402, native side (both parties on Sera)

1. Payee  -> sera.x402_invoice            -> 402 invoice against a Sera account
2. Payer  -> signs the intent with its agent key, inside its mandate
3. Chain  -> settles account-to-account in-ledger, fee in the stablecoin paid
4. Both   -> sera.get_receipt             -> same receipt shape, no bridge involved
